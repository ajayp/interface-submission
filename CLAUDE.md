# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A hackathon kit: build a knowledge system over five dated crawls ("snapshots") of a real credit union's website (Dupaco) that answers member questions with the **current**, correctly-tiered value, a source, and an honest "I don't know" when the site doesn't say. The deliverable is a folder containing `solution.py` with a `build()` function; `starter/` is the naive baseline to copy from. The data is shared for this event only — don't redistribute it. Answers may use only the snapshots (no live web calls). Graded in a clean Python 3.11 environment; the hand-in also needs `requirements.txt` (every package) and a short `NOTES.md` (how we decide what's current, which API keys are needed). Grading uses the organizers' own copy of `harness/` and `eval/`, so editing them here changes nothing, and hard-coding public answers won't help on the hidden set.

## Current design (read NOTES.md for the full write-up)

- **Query understanding (default: OpenAI Decisions API, `decisions_understanding.py`):** one `/v1/decisions` call (runs `gpt-6-luna`, labels only, ~0.3 s) gives the section, rate type and whether a past date is asked; search words come from `synonyms.py`. `MY_SOLUTION_QU_ENGINE=luna` rolls back to the older single `gpt-6-luna` JSON call (~1.75 s, `query_understanding.py`). Accuracy was equal on the public set (0.849 vs 0.847, 3 runs each); known loss: dup-104 (lobby hours).
- **Fact path (GraphRAG-style, in memory):** every distinct rate table is extracted once at loading time into facts with source,
  page type, effective/publish dates and website copy (`facts.py`). Rate/fee questions are answered from the winning facts.
  Text path is the fallback.
- **conflicts() = `conflicts_v2.py`:** contradictions in the newest website copy only: rate tables read by code, rate sentences (one small `gpt-6-luna` call each), counts about Dupaco (branches, employees, members, assets, counties served). 39 entries without a key, 40 with one (17 s on the real data). ## Decisions so far

- **Decision (user, 2026-11-16): A fact that exists only on a page missing from the newest snapshot is not answered for a current question; it is answered for a dated question from the snapshot that has the page.** The carry-forward idea (keep a vanished page's last copy at the lowest trust, `tasks/todo.md` plan) is NOT built. Reasons: only 1 of the 17 vanished pages (the Visa comparison chart PDF) holds a fact found nowhere else; the assignment says without `as_of` answer from the newest snapshot; dated questions already see vanished pages because they use the snapshot that has them; a should-refuse question answered from an old PDF would score zero. The selftest fixture's lost-card fee question (page only in the older snapshot) therefore stays "I don't know" for a current question, on purpose.

- Our submission lives in `my_solution/` (any folder except `starter/`).
- Hardening (2026-11-16): `requirements.txt` pins `openai>=3.51,<4` (the code needs `client.decisions.create`); `solution.py` no longer crashes when the folder has no `harness/` parent; one clear warning at loading time if the model or the Decisions API cannot be reached. With no key the system still returns raw page text (user decision: leave as is).
- LLM provider: **OpenAI** (the user's credits). The key goes in an environment variable, never in the repo; `NOTES.md` must name it. Heavy LLM work belongs in `ingest` (untimed); `answer` must stay near the 2 s p95 target and be deterministic.
- Approach: a general extraction pipeline (structured facts with history), proven first on small eval subsets grouped by category, then widened category by category.
- **Principle: general rules only, never fit the practice questions.** The hidden set rewords and extends them, so a prompt rule or search tweak must make sense for any member question, not just the one that failed. Accept a known miss rather than add a question-shaped rule. This is early days: work in slices, see what holds up, and evolve the architecture (embeddings, ingest-time fact extraction, GraphRAG / a knowledge graph) only when slices show the need.
- Build order: get retrieval right first with BM25 and no LLM, scored by a retrieval-only metric on the slice (hit@k, trap-above-gold); add the OpenAI answer call only after that. Ingest-time LLM extraction is a later slice (budget: $1 total).
- Source tiers (record in `NOTES.md` too): **tier 1 authoritative** = rate sheets (`/rates`, `/business-rates`) first, then product/service pages (`/personal/...`, `/business/...` except `business/resources`, `/about/...`, `/contact`, `/checking`), with promo/landing pages (`*-lp`, `/switch-and-earn`) at the bottom of tier 1. **Tier 2** = newsroom, `learn/blog`, `business/resources` articles, dated paths (`/2018/...`, `dupacodaily/...`), calculators (their rate tables go stale, e.g. 5.34% "effective 1/1/2026" vs the real 5.39% "effective 08/31/2026"), and PDFs/files by default. A page's "Rates are effective as of <date>" note is a freshness signal.
- Slice 1 = `eval/subsets/slice1_rates.jsonl` (10 rate questions: stale_trap, tier_disambiguation, one as_of).
- Answer step (slice 1): one `gpt-6-luna` call per question (the feature-skill tier map: RAG/Q&A over provided context → Luna), Responses API, reasoning effort `none` + temperature 0, strict JSON schema, prompt in the feature-skill OpenAI guide layout (`my_solution/prompt.py`), checked by the feature-skill `prompt-linter` (compatible, low risk). Model guides live in `ajayp/feature-skill/models/`: read them before choosing or changing a model. Answers are cached per (question, snapshot), so repeats in a run are identical; Luna at temperature 0 is still not fully deterministic across separate calls (the input id is a hash of the request so identical input gives an identical prompt). 6 s timeout, one retry. Override the model with `OPENAI_MODEL`.
- Known slice-1 limits (accepted, not tuned for): category questions ("what are the mortgage rates right now?") are summarized inconsistently (structured facts from ingest-time extraction are the planned fix); mortgage answers vary in which APRs they add, which can cost paraphrase consistency.
- Retrieval scope: `my_solution/retrieval_eval.py` judges only whether the right evidence reaches the top-k chunks (k=8, exact duplicates merged, every alias URL kept for citing). Things BM25 cannot do by design (picking a tier from a table, knowing 2025 is inside "2024-27", reading "right now" as "show numbers") are judged at the answer step, not tuned into search. Known scorer looseness: bare numbers like "12.5" can mark an unrelated chunk as gold.

## Commands

Run from the repo root (`python harness/...` needs 3.9+; the user keeps a local `venv/`, which is not in the repo):

```bash
# Score a submission against the public eval (first run unpacks snapshots_zip/*.zip into snapshots/)
python harness/run_eval.py --submission starter --eval eval/public_eval.jsonl

# Point at your own folder instead of starter/
python harness/run_eval.py --submission my_solution --eval eval/public_eval.jsonl

# Optional flags: --repeat-sample N (consistency re-asks, 0 = off), --out DIR (default results/),
# --judge (LLM-graded free text; needs ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN plus the anthropic and
# pydantic packages), --conflicts-gold FILE (the real gold list is not shipped), --snapshots DIR (default snapshots/)

# Score a subset (proof-of-concept slices): write a filtered copy of the eval and point --eval at it
python harness/run_eval.py --submission my_solution --eval eval/subsets/<slice>.jsonl

# Tiny selftest fixture: the only local way to exercise conflicts() scoring
python harness/run_eval.py --submission my_solution --snapshots harness/selftest/snapshots \
    --eval harness/selftest/eval.jsonl --conflicts-gold harness/selftest/conflicts_gold.json --out results/selftest
```

There is no test suite or linter; `harness/selftest/` (2 tiny snapshots, 5 eval items, a 1-entry `conflicts_gold.json`) is a fixture, not a test runner. Without `--conflicts-gold` the conflicts pillar is skipped and the remaining weights are renormalised, so public-eval scores don't reflect `conflicts()` at all. The run writes `results/report.json` (pillar scores, per-category breakdown) and `results/per_question.jsonl` (per-question `matched`/`missed`/`trap_hits`/latency/answer) — read the latter to see which questions you miss, not just the score.

## Architecture

- `harness/contract.py` — the fixed interface. A submission's `build()` returns an object with `ingest(snapshot)`, `answer(question, as_of=None) -> Answer`, and `conflicts() -> list[Conflict]`. Don't rename anything; the hidden grader plugs the folder into the same harness. Only stdlib dataclasses cross the boundary, so internals can use any stack (add `requirements.txt`; document needed API keys in `NOTES.md`).
- `harness/run_eval.py` — loads snapshots oldest→newest from `snapshots/<id>/manifest.json` + `pages/*.md`, calls `ingest` once per snapshot (30 min total limit, untimed), then `answer` per eval item on a single worker thread (60 s timeout; a crash/timeout scores 0 — and a timed-out call keeps occupying that one thread, delaying the questions after it), re-asks a sample for consistency (every ~2nd item with the default `--repeat-sample 20`), then optionally scores `conflicts()`. It loads `solution.py` by file path and also puts the submission folder on `sys.path`.
- `harness/scoring.py` — the exact scorer; read it before designing answer text. Key behaviours:
  - `must_include` facts are matched by **numeric value** for pure numbers/rates (`3.5%` == `3.50 %`), otherwise as normalized substrings.
  - Any `must_not_include` value appearing in the answer zeroes correctness (stale/other-tier values) — never hedge by listing multiple numbers.
  - `should_refuse` items need `confident=False` or a refusal phrase **and no numbers** beyond those in the question.
  - Source credit (+15%) is a path-level URL match against `expected_sources`.
  - Final = accuracy 55% + conflicts 15% + consistency 15% + speed 15%; consistency and speed are multiplied by accuracy. Consistency compares the *set of numbers* in answers across reworded questions (same `group`) and repeat asks, so answers must be deterministic. Speed uses p95 latency (≤2 s full marks, 0 at ≥20 s) — keep `answer` fast, do heavy work in `ingest`.
- `starter/solution.py` — naive baseline: keeps only the latest copy of each page, returns the paragraph with the most word overlap, ignores `as_of`, returns no conflicts. It locates `harness/contract.py` by walking up parents, so a submission folder must live inside this repo (or copy `contract.py`'s types).
- `eval/public_eval.jsonl` — 40 practice items (`question`, `as_of`, `must_include`, `must_not_include`, `category`, `weight`, `expected_sources`, `group`). Categories: stale_trap, tier_disambiguation, temporal_as_of, conflict_resolution, current_value, list_completeness, entity_attribution, branch_info, should_refuse. Only one public item sets `as_of`; most `temporal_as_of` items have `as_of: null` and put the date in the question text ("as of May 2026", "today (October 2026)"), so question parsing must handle both. The hidden set uses the same format and scorer and includes reworded variants, `as_of` date questions, and questions about things that changed between snapshots.
- `snapshots/` — the five unpacked crawls (`01_2026-05-12_baseline` … `05_2026-09-28_latest`); "current" = the 05 snapshot. `snapshots/README.md` describes each pull. Each snapshot is "every page we had, in its newest version as of that day": most pages are re-fetched, but 3–4% of pages in snapshots 02–05 are carried over from an earlier crawl with an older per-page `fetched_at` (e.g. 05 contains pages fetched 2026-06-09). Treat per-page `fetched_at` as the observation date, not just `taken_on`. Pages do appear/disappear between snapshots (e.g. +50 in 04, +25/−3 in 05). 17 pages vanish in all (4 into 02, 8 into 03, 2 into 04, 3 into 05): 11 are tag and author index pages, 1 was renamed (Bright Savings), 1 is a `#fragment` copy of a page that is still there, and 4 are old PDF/CSV files; only the Visa comparison chart PDF holds a fact found nowhere else (see the vanished-pages decision below). Working assumption (ours, not stated by the organizers): an `as_of` question is answered from the latest snapshot with `taken_on <= as_of`.

## Data gotchas (the point of the exercise)

Pages deliberately contradict each other: stale rates left on old pages/PDFs/newsletters/press releases, expired promotions never removed, rate vs APY shown on different pages, and tiered tables (by balance, term, or loan amount) that look like conflicts but aren't. Qualifiers (6- vs 12-month, "Prime Checking" vs "Prime Business Checking", rate vs APY, loan-amount tier) distinguish facts rather than signal conflicts. Keep per-fact history (value, snapshot, URL) rather than just the latest page copy, and decide source-precedence rules explicitly (e.g. official rate table over blog/press release; newer snapshot over older).
